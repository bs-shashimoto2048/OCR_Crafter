# Issue作成ガイド

**Issueはメモではなく、実装・レビュー・完了判定に使える仕様書です。** 「あとで思い出せればいい」程度のメモとしてIssueを書かないでください。このIssue本文だけを読んだ人（人間のレビュアーでも、Claude CodeやCodexのようなAIコーディングエージェントでも）が、追加の質問なしに実装・レビュー・完了判定を行えることを目指してください。

基本フローは [GITHUB_ISSUES_WORKFLOW.md](GITHUB_ISSUES_WORKFLOW.md)、AIエージェントへの指示方法は [AI_AGENT_WORKFLOW.md](AI_AGENT_WORKFLOW.md) を参照してください。

## 良いIssueの条件

- **対象範囲と対象外が明記されている**（何をやり、何をやらないかが分かる）
- **受け入れ条件が具体的でチェックできる**（「良くする」ではなく「〇〇画面で〇〇できる」）
- **現在の動作と期待する動作が両方書かれている**（差分が分かる）
- **影響範囲（UI/Backend/API/データ/Dataset/Experiment/Model/Evaluation/Benchmark/監査）が確認されている**
- **実装済みの内容と推測・要望が区別されている**

## 悪いIssueの例

- 「モデル管理を改善してほしい」（何をどう改善するのか不明。対象範囲が無い）
- 「Benchmarkが遅い気がする」（再現手順・実行環境・実際の数値が無く、調査すら始められない）
- 「TrOCRに対応する」（[GITHUB_ISSUES_WORKFLOW.md](GITHUB_ISSUES_WORKFLOW.md) の「Issueを分割する基準」を参照し、分割してください）
- 受け入れ条件が「バグが直っていること」だけ（何を確認すれば直ったと判断できるのか分からない）

## 受け入れ条件の書き方

- チェックボックス形式で、1項目1条件にする
- 「〇〇できる」「〇〇が表示される」など、実際に確認できる動作で書く
- テストの追加が必要な場合は、受け入れ条件に含める（例:「回帰テストを追加し通過する」）
- 曖昧な形容詞（「使いやすく」「高速に」）だけで終わらせず、確認可能な基準に落とし込む

```text
悪い例: パフォーマンスを改善する
良い例: 1000件のジョブ一覧取得が2秒以内に応答する（現状: 5秒）
```

## 対象範囲と対象外の書き分け

- **対象範囲**: 今回のIssueで実装・修正する画面・機能・エンジンを明記する
- **対象外**: 関連はするが今回は扱わない範囲を明記する。特に「将来の拡張候補ではあるが今回のスコープではない」ものは対象外へ明記し、対象範囲に紛れ込ませない

対象外を書かないと、実装中にスコープが際限なく広がったり（スコープクリープ）、逆にレビュアーが「これも対応すべきでは」と誤解したりします。

## UI・API・データ影響の確認方法

Issue作成前に、実際のコード・画面・APIを確認してください。

- **UI**: 対象画面のファイル（`frontend/src/views/*.jsx`）と [16_SCREEN_SPEC.md](../16_SCREEN_SPEC.md) を確認する
- **API**: `src/app/main.py` と [06_API_REFERENCE.md](../06_API_REFERENCE.md) を確認し、既存エンドポイントの有無・パラメータを把握する
- **データ**: `config/settings.yaml`・`data/projects/<id>/` 配下の実際のファイル形式を確認する（推測しない）
- **Dataset/Experiment/Model/Evaluation/Benchmarkへの影響**: それぞれ `dataset_registry.py`・`experiment_tracker.py`・`model_registry.py`・`ocr_evaluation.py`・`benchmark.py`/`benchmark_center.py` に影響するか確認する
- **監査への影響**: 新しい操作を追加する場合、`services/audit_log.py` の `AUDIT_ACTIONS`/`ACTION_MIN_ROLE` に追加が必要かを確認する

不明な場合は「未確認」ではなく、実際に調べた上で記載してください。調べても分からない場合は、次の「実装前の調査が必要なケース」を検討してください。

## 実装前の調査が必要なケース

以下に該当する場合は、Feature/Bug Issueをいきなり書くのではなく、先に Investigation Issue を作成してください。

- 外部ライブラリ・新エンジン（TrOCR等）の技術的な実現可能性が不明
- 複数の実装方式が考えられ、比較検討が必要
- 既存の不具合の原因が特定できていない（原因調査Issue）
- 影響範囲が広く、設計方針を決めてから実装したいもの（例: 既存4エンジンの抽象化見直し）

## Issue分割の判断

1つのIssueが以下に当てはまる場合は分割を検討してください。

- 受け入れ条件が10項目を超える
- UI・Backend・API・複数の既存機能（Dataset/Experiment/Model/Evaluation/Benchmark）すべてに影響する
- 完了までに複数回のレビューサイクルが必要になりそう
- 「まず調査してから実装したい」部分と「明らかに実装すればよい」部分が混在している

分割の考え方・具体例は [GITHUB_ISSUES_WORKFLOW.md](GITHUB_ISSUES_WORKFLOW.md) の「Issueを分割する基準」を参照してください。

## 親Issue・子Issueの扱い

- 大きな取り組み（例: TrOCR対応）は、概要を説明する**親Issue**と、実装単位に分割した**子Issue**に分ける
- 親Issueには、子Issueへのリンク一覧（`- [ ] #123 技術調査` のようなタスクリスト）を記載する
- 子Issueには、親Issue番号を「補足資料」または本文冒頭に明記する
- 親Issueは実装を行わず、進捗の集約・全体の受け入れ条件（すべての子Issueが完了しているか）のみを持つ

## チェックリストの使い方

- Issueテンプレートの「受け入れ条件」「完了条件」はMarkdownのチェックボックス（`- [ ] `）で書く
- 実装完了時に、担当者（人間・AIエージェントいずれも）が1項目ずつ確認してチェックを付ける
- チェックが付いていない項目が残っている場合は、Pull Requestをマージしない

## 実装中に仕様変更が生じた場合の手順

1. **先にIssue本文またはコメントを更新する**（Pull Requestの説明文だけに書かない）
2. 対象範囲・対象外・受け入れ条件のうち、変更が必要な箇所を明記する
3. 変更理由をコメントに残す
4. 大きな変更の場合は、実装を一時中断し仕様レビューをやり直す
5. Pull Requestの説明にも、Issueと異なる実装をした場合はその旨と理由を明記する

**Pull Requestだけで仕様を追加・変更しないでください。** Issueが常に一次仕様であるという原則を保つためです。
