# AIエージェント向け運用ガイド

Claude Code・Codexなど、AIコーディングエージェントへGitHub Issueを渡して実装してもらう際のルールです。人間の開発者がAIエージェントに作業を依頼する場合も、AIエージェント自身がこのリポジトリで作業する場合も、このガイドに従ってください。

Issueの書き方は [ISSUE_WRITING_GUIDE.md](ISSUE_WRITING_GUIDE.md)、全体フローは [GITHUB_ISSUES_WORKFLOW.md](GITHUB_ISSUES_WORKFLOW.md)、コミット・ブランチ・PR規約は [../../CONTRIBUTING.md](../../CONTRIBUTING.md) を参照してください。プロジェクト固有のコーディングルール（言語・禁止事項・編集禁止箇所等）は [../../CLAUDE.md](../../CLAUDE.md) にあります。

## 作業開始時

1. **Issue本文とコメントをすべて読む**（本文だけでなく、後から追記されたコメント・仕様変更も確認する）
2. **関連ファイルを調査する**（対象の画面・サービス・APIエンドポイントを実際に開いて確認する。推測しない）
3. **既存実装を再利用する**（同じ目的の関数・コンポーネント・パターンがすでにあれば流用する。新規実装を優先しない）
4. **Issueの対象外を確認する**（対象外に書かれている範囲まで手を広げない）
5. **不明点がある場合は推測で実装しない**（Issueへ質問を追記する、またはユーザーに確認する）
6. **作業計画を提示する**（何をどの順で変更するか、着手前に簡潔に共有する）
7. **Issue番号に対応するブランチを使用する**（[CONTRIBUTING.md](../../CONTRIBUTING.md) の命名規則に従う）

## 実装時

- **無関係なリファクタリングをしない**（Issueのスコープ外のコード整形・書き換えをしない）
- **既存機能を置き換えず、拡張可能なら拡張する**（大規模な書き直しより既存パターンの踏襲を優先する）
- **UIだけでなく永続化・API・テストまで確認する**（画面が動いて見えるだけで完了にしない）
- **事実に基づいてドキュメントを更新する**（実装していない内容・未確認の内容を書かない）
- **テストを削除・弱体化して通さない**（失敗するテストをコメントアウトする、アサーションを緩めて通す、は禁止）
- **一時的なモックで完了扱いにしない**（本実装が必要な箇所をモックのまま残さない）
- **既存データとの互換性を考慮する**（`config/settings.yaml`のキー追加・データ構造変更は後方互換を維持する。[CLAUDE.md](../../CLAUDE.md) の「絶対に変更してはいけない仕様」も参照）

## 完了時

- **Issueの受け入れ条件を1項目ずつ確認する**（チェックが付けられない項目が残っていないか）
- **テスト**（バックエンド: `python -m pytest -q` / フロントエンド: `cd frontend && npm test`）
- **Build**（`cd frontend && npm run build`）
- **`git diff`**（意図した変更のみになっているか確認する）
- **`git status`**（無関係なファイルが混ざっていないか確認する）
- **ドキュメント更新**（該当する場合。[CONTRIBUTING.md](../../CONTRIBUTING.md) の「ドキュメント」チェックリストを使う）
- **Commit**（[CONTRIBUTING.md](../../CONTRIBUTING.md) のCommit規約に従う。Issue番号を含める）
- **Push**（Issue番号に対応するブランチへ。mainへの直接pushは既存の運用に従う場合のみ）
- **PR作成用の説明文を提示する**（`.github/PULL_REQUEST_TEMPLATE.md` の各項目を埋めた内容）

## 禁止事項

- **Issueにない機能の追加**（「ついでに」の機能追加をしない）
- **根拠のない仕様変更**（コード・UI・APIで確認していない変更を仕様として書かない）
- **存在しないAPIや画面のドキュメント化**（実装されていない内容は「現時点では未実装」と明記する）
- **テスト未実施での完了報告**（実行していないテストを「通過した」と報告しない）
- **mainへ無断で直接push**（Issue単位のブランチ・PRが原則。現在の運用がmain直接push中心の場合は、その運用に従いつつ、この原則へ徐々に移行する）
- **Issueを更新せずに仕様を変更**（実装中に仕様変更が生じた場合は、先にIssue本文・コメントを更新する。[ISSUE_WRITING_GUIDE.md](ISSUE_WRITING_GUIDE.md) の該当節を参照）
- **HMR状態だけを根拠に不具合修正完了と判断する**（Viteの開発サーバーはコード変更を重ねると状態不整合を起こすことがある。修正の妥当性は、静的なコード確認・実データでの検証・テストの組み合わせで担保し、「開発サーバーで直って見えた」だけで完了と判断しない）
